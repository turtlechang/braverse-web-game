誰負責什麼

把每個角色想成流水線上的關卡。每個關卡只做自己該做的事，問題會比較好追。

角色 白話說明 它不該做什麼
使用者 提出需求、看 Preview、決定要不要合併。 不要直接把未檢查的東西推進 main。
Codex 像指揮官：先讀規則、拆任務、驗證結果、帶你走流程。 一般情況不直接改專案檔，除非你明確同意例外。
OpenCode Go 像施工團隊：依 Codex 指令新增、修改檔案。 不擅自還原你的其他修改，不提交密鑰。
GitHub Actions 像自動驗收員：每個 PR 跑測試、Lint、Build。 不部署、不保存 Vercel Token。
Vercel 像展示間與正式門市：PR 給 Preview，main 更新正式站。 不取代 GitHub CI 的品質檢查。

平常怎麼用

你每天真正需要記住的是這五步。

開新需求 跟 Codex 說你要改什麼。Codex 先確認目標、風險與完成標準。
開 PR 改完後推分支，建立 Pull Request，不直接推 main。
看兩個燈 GitHub CI 要綠燈，Vercel Preview 要能打開。
看網頁成品 在 Preview 直接玩或檢查畫面，確認不是只看程式碼。
合併 main 確認後合併，Vercel 自動更新正式網站。

兩份 workflow 在做什麼

這兩份檔案是 GitHub Actions 的設定。它們只做驗證，不做部署。

.github/workflows/ci.yml

這是每次 PR 與 main push 自動跑的基本檢查。

  • 觸發時機：所有 PR、push 到 main
  • Node.js：22
  • 權限：contents: read
  • 指令：npm ci、npm test、npm run lint、npm run build

.github/workflows/ai-browser-validation.yml

這是需要更完整瀏覽器驗證時，手動按下去跑的檢查。

  • 觸發時機：手動 workflow_dispatch
  • 先執行：npm run build
  • 安裝：npx playwright install chromium --with-deps
  • 驗證：npm run test:ai:browser
  • 失敗時：上傳 test-results/，保留 7 天

紅燈怎麼辦

紅燈不是壞事，它是在阻止問題進正式站。照這張表處理就好。

看到什麼 代表什麼 下一步
CI failed 測試、Lint 或 Build 有一關沒過。 打開失敗步驟，看錯誤訊息；先修本機，再 push 更新 PR。
Preview protected / Authentication Required Vercel Preview 有登入保護。 用已登入 Vercel 且有權限的瀏覽器開啟；這不等於部署失敗。
Vercel build failed Vercel 建置環境跑不過。 看 Vercel Deployments 的 build log，通常是 Node 版本、install 或 build 指令問題。
AI browser validation failed 完整瀏覽器對戰驗證有問題。 下載 GitHub Actions 的 test-results artifact，看截圖與報告。
main 不能直接 push 分支保護正在正常工作。 建立分支與 PR，等 CI 綠燈後再合併。

三個不要

這三件事最容易讓流程變亂，請固定避免。

不要放 Vercel Token GitHub Actions 不負責部署，所以不需要 VERCEL_TOKEN、VERCEL_ORG_ID、VERCEL_PROJECT_ID。
不要直接 push main 正式站更新要走 PR，讓 CI 與 Preview 先擋問題。
不要提交產物 test-results/、dist/、node_modules/ 都不要進 Git。

最後檢查清單

每次準備合併前，看這張清單。

✓
PR 的 Test, Lint & Build 是綠色。
✓
Vercel Preview 能打開，畫面與操作正常。
✓
README 或文件若有變更，內容沒有宣稱未完成事項已完成。
✓
沒有把密鑰、dist/、test-results/、node_modules/ 放進 commit。
✓
需要完整對戰驗證時，手動跑 AI Browser Validation。
✓
合併後確認正式網站仍能載入。
