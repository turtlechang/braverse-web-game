# 實體卡圖與獨立驗收方法

本方法適用於任何執行本專案逐卡轉換／驗證的模型。驗收單位是「卡號／版本／語言／
異圖的每個效果與分支」，不是一次工具呼叫、一張卡曾出現 trace 或一份全綠報告。
沿用現行任務矩陣，不另建重複追蹤系統；未獲授權的修改／promote 仍不可執行。

## 1. 先看實體卡圖，再建立預期

1. 取得使用者提供的實體卡照片或官方完整卡面影像，實際用可視工具打開檢查。
   JSON、OCR、卡牌詳情文字與其他模型的轉述只能交叉參考，不能當作「已看過圖」。
2. 確認卡號、版本／語言、異圖、卡名、種類、LV／HP、顏色、能量圖示、技能名、
   全部時機標記、攻擊傷害與費用、技能／Then／FLIP 原文。注意括號、可選詞、
   否定詞、主客體、數量與標點；不能用「這類卡通常如此」補字。
3. 保存來源 URL 或本機檔名、圖片 SHA-256（工具可取得時）、目視日期、覆核者及
   完整轉錄。圖示以明列圖例轉成文字；只容許已確認的換行／排版等價，不模糊忽略
   數字、費用、顏色或條件。異圖逐筆看圖後才決定是否能共用效果案例。
4. 先寫下依圖解讀的「印刷片段 → 預期行為」，再查 adapter／runtime。
   不准以實際輸出生成 expected、直接更新 snapshot，或照抄 adapter 當測試預期。
5. 圖文差異列出「圖上原文／來源欄位／runtime／UI」四欄。圖不清、圖缺失或裁定
   有歧義時標 `待確認` 並列具體缺口；可以繼續不依賴該資料的盤點，不能猜測通過。
   若疑似官方勘誤，查最新官方規則／FAQ，保留原圖與裁定依據；不把過期印刷當作
   可覆蓋最新裁定的理由，也不自行改寫官方原始文字掩蓋衝突。

## 2. 每個印刷片段都要有獨立契約

將每個技能、攻擊、Then、FLIP、被動／陷阱拆成可追溯片段，逐項記錄：

| 維度 | 必須說清楚的預期 |
|---|---|
| 時機與條件 | 誰的回合／階段、觸發事件、來源所在區域、每回合限制、門檻及計數來源 |
| 支付 | 指定色／任意色、張數、支付來源、活躍要求、可選／減費／替代支付 |
| 代價 | 哪個區域的哪些卡／HP、數量、先後順序、代價不足、來源因代價離場 |
| 目標 | 己方／對方、區域、卡種、顏色、LV／HP、排除自身、數量、可選0、重複限制 |
| 結算 | 精確數值、卡牌去向／狀態、持續時間、Then依賴、FLIP／昏厥插入及後續順序 |
| UI | 應出現哪些候選、費用與說明、確認／取消／返回／略過、不可操作的原因 |

不適用寫 `N/A + 原因`，不能留白。每個來源片段都要對應 runtime 與案例；一個效果
成功不代表同卡其他效果也成功。先比對契約，再使用既有 shadow／strict 工具找缺漏。

## 3. 以條件與邊界設計案例，不只做一正一反

- 每個有效果的分支至少有真正生效的合法案例與相關負向案例；`up to` 選0、取消或
  合法 no-op 另列，不能充當正向生效。被動效果以實際狀態差異或攻擊結果證明。
- 每個獨立限制各有負向：付款不足、錯色／疲勞、條件未達、錯誤主客體／區域／
  LV／HP、來源離場、第二次發動或錯誤時機。一次只改被測限制，其餘資源保持合法。
  例如有足夠綠色能量時測「支援差1不減費」，不能拿完全無能量代替條件負向。
- 數量測0／1／上限／超選，門檻測前一格／剛好／超過；不適用不硬湊案例。
  Then另測前段付費／略過／失敗及中途來源或目標離場；有順序選擇時以反向點選
  驗證按玩家順序處理，而不是剛好符合陣列預設順序。
- 共用規則以分層／組合案例檢查交互作用，不要求枚舉所有笛卡兒組合；卡圖專屬
  邊界仍須保留，不可拿同類型另一張卡的通過結果取代。

## 4. Browser 必須核對實際操作與精確結果

先依專案要求 build，使用當下可用的瀏覽器工具；不能指定某模型才可完成。
初始局面可由 fixture／情境 UI 建立，但效果驗證需實際點擊 UI，不能直接呼叫規則
或改狀態代替玩家操作。不要 force-click 穿過遮擋，否則不能證明可操作性。

每條案例記錄操作前、選取／付款中、結算後：

- 卡圖真的載入且與已覆核圖片一致；卡名／卡號／時機與效果說明一致，fallback
  或卡背不能算實圖通過。圖片網路失敗屬素材阻塞，不可吞錯後宣稱完整UI通過。
- 完整合法候選集合與被排除的反例、選取數量、停用原因；不是「有一顆可點按鈕」。
- 支付哪些支援卡、哪張卡被棄置／移區、哪個目標HP或攻擊力改變多少；未選目標與
  其他牌區不應發生的變化也要核對。HP、支援狀態、手牌／牌庫張數需區分效果與
  正常登場／戰鬥流程造成的差值，不能把正常流程誤算成效果。
- 取消／返回／略過後是否按規則保留或返還資源、有無重複扣款、pending是否清除、
  能否繼續合法回合；點得到、選得對、結算對，三者各有證據。
- 在本次範圍要求的桌機／平板尺寸操作，檢查遮擋、點擊命中、捲動、數量與提示，
  保存選取／付款畫面和結算畫面、console／React／network錯誤。不能只靠DOM文字
  或截圖其中一種證明全流程；手機僅在授權範圍內增加。

公開 trace 是輔助證據，不能只靠 command存在、關鍵字或「resolve完成」判通過。
expected command／順序必須事前指定，不能從觀測結果取第一個command作預期。
不把對手手牌、未知牌庫順序、未公開HP或raw payload放進報告；私密精確狀態應在
規則測試檢查，Browser只看玩家依法可見的資訊。

## 5. 驗證案例真的會抓錯

新建或大幅修改共用轉接／驗收方法時，挑高風險代表案例做定向變異檢查：例如傷害
+1、移除付款／顏色限制、放寬門檻、交換Then。原版通過，同一組獨立預期必須能
抓到對應錯誤。用測試內的不可變副本或已授權隔離環境，不污染正式檔案。

只修改「觀測JSON」來測比較器，須標為驗收器測試，不宣稱已測引擎變異；只驗證
少數mutant也不得報整體mutation coverage。日常沿用有效的共用證據，不每張卡
重做同一套變異測試；新增未覆蓋句型／根因時才補。

## 6. 完成判定、失效與交接

每張卡依序過「卡圖目視→獨立契約→轉接／規則→Browser合法與各必要負向→回歸」
才可增加逐卡cursor。任何缺證、待確認、失敗都保留原卡號與原因；不得跳過後稱整批
完成。promote仍須明確授權及全部閘門證據，不因現有CLI未強制讀取Browser報告就
放行，也不自行新增／修改驗收工具來擴張當次任務。

記錄來源圖／文字版本、規格、HEAD與未提交差異、測試／driver版本、命令、尺寸、
結果及證據位置。圖片、卡文、adapter／共用規則／UI／fixture或預期變動時重查
受影響案例；無法證明舊證據仍適用時標過期。雜湊是追溯輔助，不是目視或語意正確
的保證。工具不具備時可用等價人工矩陣；缺少真實證據時仍不能通過。

回報分開列「卡圖核對、轉接契約、規則測試、局部test-state Browser、正式牌組流程、
線上同步」。局部fixture只能說明該局面，不代表正式逐卡完整對局。統計以卡號／
變體及效果／分支為分母，另記初次轉換缺陷與驗收後漏失缺陷；未量測就寫未量測，
不拿全綠測試率推算正確率或承諾零錯誤。換模型交接時留下當前卡號、逐字轉錄、
獨立預期、已通過案例、缺口及下一步，不能只留下「verified」字樣。
